# Developer Guide — `dw` (Diff Direct Writer)

This document is the developer-facing companion to `README.md`. It explains
*why* `dw` behaves the way it does, *how* to produce a valid `diff.txt`, and
*how* to diagnose every failure mode. It assumes familiarity with unified
diffs and the strict behavior of `git apply`.

---

## 1. What `dw` actually does

`dw.sh` reads a single text file (`diff.txt`) containing two logical parts:

```text
<line 1>       absolute path to a Git working tree
<line 2 .. EOF> unified diff (the output of `git diff`)
```

For each `diff --git` block in the diff, it:

1. Extracts the block into a temporary per-file patch.
2. Runs `git apply --check` on that patch, then retries with
   `--ignore-whitespace` if the strict check fails.
3. If the check passes, runs `git apply` to modify the file.
4. If the check fails but the patch is reversible (`git apply -R --check`
   passes), reports `[SKIP]` because the patch is already applied.
5. Otherwise, reports `[FAIL]` with the error returned by `git apply`.

The options (`-u`, `-c`, `-b`, `-a`, `-s`, and `-n`) are layered on top of
this per-file processing loop.

> **`git apply` is the gatekeeper. If it cannot parse or apply a hunk, `dw`
> cannot apply that file.**

---

## 2. The one rule that matters

**Never hand-write hunk (`@@`) headers or the `index` line.**

`git apply` validates each hunk header against the hunk body:

| Field in `@@ -a,b +c,d @@` | Required value |
|---|---|
| `a` | First line number in the old file |
| `b` | Number of context (` `) and removed (`-`) lines in the hunk body |
| `c` | First line number in the new file |
| `d` | Number of context (` `) and added (`+`) lines in the hunk body |

If any count is incorrect, `git apply` can reject the patch with
`corrupt patch at line N`. Multibyte Persian and Arabic text does not change
the line-counting rule, but makes manual byte-level patch construction even
less reliable. `git diff` calculates the ranges from the actual file content.

The `index <old-sha>..<new-sha> <mode>` line is also generated by `git diff`.
A hand-written line such as `index 0000000..1111111 100644` is a warning sign:
the patch may have been manually assembled, and its hunk metadata should not
be trusted.

## 3. Producing a valid `diff.txt`

### 3.1 End-to-end procedure

```bash
REPO=/path/to/your-repo
OUT=/path/to/dw-linux-ubuntu/diff.txt

# 0. Start with a clean working tree for the files being changed.
cd "$REPO"
git status --porcelain
# Optional: restore only the files you intend to modify.
git checkout -- <files-you-will-change>

# 1. Modify the files. Any editor or tool can be used.

# 2. Inspect the changes.
git status --porcelain
git diff --stat

# 3. Write the repository path on line 1, followed by the Git diff.
{
  printf '%s\n' "$REPO"
  git diff --no-color
} > "$OUT"

# 4. Validate the generated diff.
grep -c '^index ' "$OUT"
grep -c '^@@ -' "$OUT"
git apply --check "$OUT" && echo "PASS" || echo "FAIL"

# 5. Restore the working tree so dw.sh can apply the same patch.
git checkout -- .

# 6. Run dw.
cd /path/to/dw-linux-ubuntu
./dw.sh
```

Steps 3–4 are the non-obvious parts. The remaining steps are standard Git
working-tree hygiene.

### 3.2 Restricting the diff to specific files

```bash
{
  printf '%s\n' "$REPO"
  git diff --no-color -- src/data/projects.ts src/data/tech-usage.ts
} > "$OUT"
```

### 3.3 Why restore the working tree before running `dw.sh`

If the files remain modified, `dw.sh` may recognize the changes as already
applied and report `[SKIP] already applied`. That is safe, but:

- `-u` (undo) will have nothing from this run to reverse.
- `-c` (commit) may have nothing new to commit.
- `-a` (archive) may not archive the expected newly applied patch.

Restoring the relevant files first makes `dw.sh` responsible for applying
the patch, which is the expected workflow for its recovery options.

If the changes are already committed or you intentionally want to retain
ownership of the working-tree changes, do not run `dw.sh` to apply them.
Commit or manage those changes directly with Git.

### 3.4 Helper script: `make-diff.sh`

Place this script next to `dw.sh`:

```bash
#!/usr/bin/env bash
# make-diff.sh — produce a dw-compatible diff.txt safely
set -euo pipefail

REPO="${1:-$(pwd)}"
OUT="${2:-./diff.txt}"

REPO="$(cd "$REPO" && pwd)"
cd "$REPO"

if [ -z "$(git status --porcelain)" ]; then
  echo "error: working tree is clean; make changes first" >&2
  exit 1
fi

{
  printf '%s\n' "$REPO"
  git diff --no-color
} > "$OUT"

IDX=$(grep -c '^index ' "$OUT" || true)
HDR=$(grep -c '^@@ -' "$OUT" || true)

echo "index headers: $IDX"
echo "@@ headers   : $HDR"
echo "written to   : $OUT"

if [ "$IDX" -lt 1 ] || [ "$HDR" -lt 1 ]; then
  echo "error: generated diff is empty or has no standard hunks" >&2
  exit 1
fi

if git apply --check <(tail -n +2 "$OUT") >/dev/null 2>&1; then
  echo "ready: run ./dw.sh"
else
  echo "error: git apply --check failed" >&2
  git apply --check --verbose <(tail -n +2 "$OUT") || true
  exit 1
fi
```

Make it executable:

```bash
chmod +x make-diff.sh
```

The helper validates only the diff portion, because line 1 is metadata for
`dw.sh` and is not part of a standard Git patch.

## 4. Failure modes and what they mean

### 4.1 `patch with only garbage at line N`

`git apply` encountered a line it could not parse as part of a valid patch.
A common cause is a manually written `@@` header without numeric ranges:

```diff
@@
- old
+ new
```

Some patch tools accept abbreviated headers; `git apply` requires valid
unified-diff hunk headers. Regenerate the patch with `git diff`.

### 4.2 `corrupt patch at line N`

The hunk header's declared old-side or new-side line counts do not match
the hunk body.

For example, a header may claim eight old-side and eight new-side lines,
while the body contains a different number of context, removed, or added
lines. This often happens when a patch is edited manually or generated
without calculating hunk ranges correctly.

**Do not repair the hunk header by hand. Regenerate the diff from the
modified files with `git diff`.**

### 4.3 `hunk failed at line N`

The hunk's context does not match the target file at the expected location.
The most common cause is a stale patch: the target file changed after the
diff was generated.

Regenerate the diff against the current version of the target file. If the
change must be preserved, reconcile it with the current file before
generating a new patch.

### 4.4 `index 0000000..1111111 100644`

`git apply` does not use the `index` line to apply a patch, so a placeholder
index value does not by itself cause a failure. However, it is strong
evidence that the patch was not produced by `git diff`, which in turn means
the hunk headers were probably computed by the same non-git process and may
not satisfy `git apply`'s exact-count requirement.

A patch with placeholder `index` values and correct hunk headers will apply;
a patch with placeholder `index` values and incorrect hunk headers will fail
with `corrupt patch` or `hunk failed`. Since you cannot tell which case you
have by inspection, treat `index 0000000..` as a warning and regenerate the
patch with `git diff`.

### 4.5 All files report `[SKIP] already applied`

The target files already contain the changes represented by the patch.
Possible causes:

- The changes were applied manually and the working tree was not restored.
- `dw.sh` was run more than once with the same `diff.txt`.

This is the expected idempotent behavior; it does not necessarily indicate
an error.

### 4.6 `repo folder not found` / `line 1 ... must be the repo path`

Line 1 of `diff.txt` must contain the repository path by itself, without
quotes or surrounding whitespace.

The path may be absolute or use a supported home-directory or WSL-style
Windows form. Do not place labels such as `repo: ` in the path unless the
script explicitly documents that syntax.

If line 1 starts with `diff --git`, `---`, `+++`, `@@`, or a Markdown code
fence, the repository path is missing. Add the path as the first line.

### 4.7 `no terminal to ask for confirmation`

A non-interactive process (for example, CI, cron, or a remote SSH command)
does not provide a TTY for an interactive `[Y/n]` prompt.

Use the documented automatic-confirmation option:

```bash
./dw.sh -y
```

## 5. Recovering from a bad run

| Situation | Recovery |
|---|---|
| `dw.sh` failed on some files | Inspect the failed files, reconcile their current contents, and regenerate `diff.txt`. |
| `dw.sh` applied files but the change must be undone | Run `./dw.sh -u`, if the last-run patch is available. |
| A commit was created with `-c` | Inspect the commit first. If it is the latest commit and has not been shared, `git reset --hard HEAD~1` may be appropriate. |
| `diff.txt` was archived with `-a` | Use the documented restore workflow, for example `./dw.sh -u -r <repo>`, if supported by the installed version. |
| A preview is needed without writing files | Run `./dw.sh -n`. |

**Caution:** `git reset --hard` discards uncommitted changes. Verify the
working tree and commit history before using it.

## 6. Interaction with `git apply` flags used by `dw.sh`

The script uses a small, fixed set of `git apply` options:

| Flag | Purpose |
|---|---|
| `--check` | Parse and validate the patch without writing files. |
| `-p1` (or `-p0`) | Strip path prefixes; the script may detect which level is appropriate. |
| `--whitespace=nowarn` | Suppress whitespace warnings. |
| `--ignore-whitespace` | Fallback when strict checking fails but the patch matches modulo whitespace. |
| `-R` | Reverse the patch; used to detect whether it has already been applied. |

The script does not use `--reject`, `--3way`, or fuzz-based application.
Consequently:

- A patch must apply successfully, either strictly or through the documented
  whitespace fallback.
- Failed hunks do not produce `.rej` files.
- Failure is reported by the script rather than partially accepting
  individual hunks within a file.

## 7. Design invariants

The following are intended behavioral guarantees of `dw.sh`; verify them
against the implementation when changing the script:

1. **Per-file atomicity.** A file is either fully modified or left untouched.
   If a hunk in a file fails, the file is reported as failed.
2. **Idempotency.** Running the same patch twice applies it once; a subsequent
   run detects that it is already applied.
3. **Non-destructive by default.** Existing user changes are warned about
   rather than silently reverted.
4. **Recoverability.** The applied patch is saved to `.git/dw-last.patch`
   so the undo option can reverse it.
5. **Scoped state.** Script-generated state is kept under `.git/` or the
   current working directory, according to the implementation.

These guarantees are implementation-dependent. Update this section whenever
the behavior or storage locations in `dw.sh` change.

## 8. Quick reference

| Task | Command |
|---|---|
| Produce `diff.txt` from the working tree | `{ printf '%s\\n' "$PWD"; git diff --no-color; } > diff.txt` |
| Produce a diff for specific files | `{ printf '%s\\n' "$PWD"; git diff --no-color -- a.ts b.ts; } > diff.txt` |
| Validate the diff portion | `tail -n +2 diff.txt \| git apply --check` |
| Restore tracked working-tree changes | `git checkout -- .` |
| Count hunk headers | `grep -c '^@@ -' diff.txt` |
| Count index headers | `grep -c '^index ' diff.txt` |
| Preview a run | `./dw.sh -n` |
| Undo the last run | `./dw.sh -u` |

## 9. Appendix — minimal valid `diff.txt`

```diff
/home/user/code/portfolio
diff --git a/src/App.tsx b/src/App.tsx
index d47576b..9bba323 100644
--- a/src/App.tsx
+++ b/src/App.tsx
@@ -1,3 +1,3 @@
 line one
-old line two
+new line two
 line three
```

- Line 1: absolute repository path, by itself.
- Remaining lines: Git-generated unified diff output.
- `@@ -1,3 +1,3 @@`: three old-side lines (two context and one removed)
  and three new-side lines (two context and one added).
- `index` line: metadata emitted by Git, not a manually invented placeholder.

Use this structure as the canonical input format. Any patch modification
must preserve valid unified-diff syntax and hunk counts.
